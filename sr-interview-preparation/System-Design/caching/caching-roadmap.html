A complete guide to caching, from first principles.

Caching is one of the most powerful tools in system design — and one of the hardest to get right. This guide walks you through every concept you need, in the order you need them.

If you remember only one thing

A cache is a fast, temporary storage layer that sits between your application and a slower data source. Every caching decision is a tradeoff between speed, freshness, and complexity. There is no universally correct answer — only answers that fit your specific constraints.

01 — FundamentalsWhat a cache actually is

Forget the implementation for a moment. A cache is fundamentally an answer to a single question: "I'm about to do something slow. Did I already do it recently?"

If yes — return the saved result. If no — do the slow thing, save the result, and return it. That's the entire idea. Everything else in this guide is variations on that theme.

Why caches exist: the speed hierarchy

Computers have a fundamental physics problem: fast storage is small and expensive, big storage is slow. Every system you've ever used works around this by layering storage from fastest-and-smallest to slowest-and-largest.

L1 CPU cache
~1 ns
RAM access
~100 ns
SSD read
~100 μs
Network (same DC)
~500 μs
Database query
~1–10 ms
Cross-region network
~100 ms

The gap between RAM (nanoseconds) and a database query (milliseconds) is roughly 10,000×. That's the gap caches exploit. A cache hit in RAM returns a result before a database query has even finished crossing the network.

Mental model

If a database query takes 5ms and you serve it from a Redis cache in 0.5ms, that's a 10× speedup. If you serve it from in-process memory in 0.0001ms, that's a 50,000× speedup. Caches are essentially time travel for the parts of your system you do over and over.

02 — FundamentalsThe two metrics that matter

Latency reduction

How much faster does a single request become? This is the user-facing metric — the one that decides whether your product feels snappy or sluggish.

Database load reduction

How many requests never reach the database? This is the infrastructure metric — the one that decides whether your database melts under traffic spikes.

The number that captures both is the cache hit ratio: the percentage of requests that are served from cache rather than going to the slower source.

Hit ratio math, made concrete

Imagine your app receives 100,000 requests per second. Each database query costs 5ms.

  • No cache: All 100k req/s hit the database. Your DB is probably already on fire.
  • 90% hit ratio: Only 10k req/s reach the database — 10× reduction.
  • 99% hit ratio: Only 1k req/s reach the database — 100× reduction.
  • 99.9% hit ratio: Only 100 req/s reach the database — 1000× reduction.

Notice that going from 90% to 99% is a 10× DB load improvement, not a 9% one. Hit ratio improvements compound exponentially.

03 — FundamentalsThe four places you can cache

Caching isn't one decision — it's many decisions at different layers of your stack. Each layer trades off speed, control, and consistency differently.

Caching isn't one place — it's a stack of layers, each closer to the user.

Layer 1 — Client-side cache

The user's browser or mobile app holds onto responses. Zero network cost. You have almost no control once it's been sent — you can't reliably invalidate it. Used for assets, static API responses, things that change infrequently.

Layer 2 — CDN cache

Geographically distributed edge nodes (Cloudflare, Akamai, Fastly) cache content close to users worldwide. Brilliant for static assets and even some API responses. The user in Tokyo and the user in Berlin can both get cached responses from servers ~50ms away instead of crossing oceans.

Layer 3 — Application-level (in-process) cache

A hashmap living inside your app server's memory. The fastest possible cache — no network hop at all, just a memory lookup. The catch: every app server has its own independent copy, and they diverge the moment any of them writes.

Layer 4 — Distributed cache (Redis, Memcached)

A dedicated cache service that all your app servers talk to over the network. Slower than in-process (one network hop), but every server sees the same data. The standard answer for stateless, horizontally-scaled architectures.

The core tension you'll see everywhere

The closer to the user, the faster — but the less control you have over freshness. The further from the user (closer to the DB), the slower — but the easier to invalidate. Every cache layer is somewhere on this spectrum.

04 — StrategiesCache-aside (the default)

This is the pattern you'll see most often in production. The application manages the cache directly — checking it before reading, populating it on a miss.

The application checks the cache, then falls back to the database on miss.
Pros

Cache only stores data that's actually requested. If the cache dies, your app keeps working — just slower. Simple to implement and reason about.

Cons

First request to any key is slow (the miss penalty). Stale data risk if the DB is updated by something that doesn't invalidate the cache. Vulnerable to cache stampede on popular keys.

When to use it: Read-heavy workloads where most data is hot and you can tolerate slight staleness. The default choice for most caching layers.

05 — StrategiesWrite-through

Every write goes to both the cache and the database synchronously. The cache and database are always in lockstep.

Cache and DB are written atomically. Reads always find fresh data.
Pros

Cache is never stale on reads. No "first request is slow" problem since data is pre-populated on write.

Cons

Every write is slower because you wait for both systems. Pollutes the cache with data that may never be read. Failure mode: what if the DB write succeeds but the cache write fails? Now they're inconsistent.

06 — StrategiesWrite-back (write-behind)

Write to the cache only. The cache asynchronously flushes to the database later — in batches, on a timer, or on eviction.

Writes return instantly. Data flushed to DB asynchronously in batches.
Pros

Extremely fast writes — the app returns as soon as the cache acknowledges. DB receives batched, optimized writes instead of a flood of individual ones.

Cons

Data loss risk: if the cache crashes before flushing, the writes are gone forever. Never use this for financial transactions, audit logs, or anything where durability matters.

When to use it: Write-heavy workloads where occasional data loss is acceptable — metrics, analytics events, view counters, leaderboard updates.

07 — StrategiesWrite-around

Writes bypass the cache entirely and go straight to the database. The cache is only populated when something is later read.

This is essentially "don't bother caching on write." Useful when written data is unlikely to be read again soon — logs, batch imports, audit trails. Why pay the cache-write cost for data nobody will ask for?

Tip

Write-around pairs naturally with cache-aside for reads. Many real systems use this combo: writes go straight to DB, reads check cache first and populate on miss.

Side-by-side comparison

Strategy Write cost Read freshness Failure risk Best for
Cache-aside low eventual tolerant Read-heavy general use
Write-through 2× slower strong partial writes Read-heavy + needs freshness
Write-back fastest strong data loss Write-heavy, durability optional
Write-around low eventual tolerant Write-once, read-rarely data

08 — InvalidationTTL — let time decide

The simplest invalidation strategy: every cached entry has an expiration timestamp. Once expired, it's treated as missing.

You set a TTL (Time To Live) — say, 60 seconds — when you write to the cache. After 60 seconds, the next read sees a miss, fetches fresh data from the DB, and writes it back with a new 60-second TTL.

# Redis example
cache.set("user:42:profile", profile_data, ex=300)  # 300 seconds

Choosing TTL values

The right TTL is a business question, not a technical one. Ask: "how stale can this data be before it causes a real problem for the user?"

Stock prices

~1 second. Stale prices cost real money.

Social media feed

~30 seconds. Nobody notices a brief delay.

Product catalog

~1 hour. Updates are rare; freshness rarely matters.

User permissions

~5 minutes. Revocation needs to propagate, but not instantly.

Currency conversion rates

~10 minutes. Rates change but slowly.

Static content (images, JS)

Days to weeks with versioned URLs.

09 — InvalidationEvent-driven invalidation

Don't wait for time to expire — invalidate the moment you know data has changed.

When something writes to the database, also tell the cache: "this key is stale now." There are two flavors:

Delete-on-write

On update, cache.delete(key). The next read will miss, fetch from DB, and repopulate. Simple, safe, the default choice.

Update-on-write

On update, cache.set(key, new_value). No cache miss penalty on the next read. Risk: race conditions if multiple writers update the same key.

The hardest problem in CS

"There are only two hard things in computer science: cache invalidation and naming things." — Phil Karlton. The difficulty is rarely invalidating one key — it's knowing which keys need to be invalidated when something changes. Updating a user profile might invalidate that user's profile cache, their friends list cache, every page that displays their name, every search index entry...

10 — InvalidationEviction policies

RAM is finite. When the cache fills up and you need to add a new entry, something must be removed. The eviction policy decides what.

LRU keeps "recently used" things; everything older gets discarded.
LRU — Least Recently Used

Evict whatever hasn't been accessed for the longest time. The default in most caches. Works well when recent data is likely to be re-requested.

LFU — Least Frequently Used

Evict whatever has been accessed the fewest times overall. Better when popularity matters more than recency. More complex to track.

FIFO

Evict the oldest entry, regardless of access pattern. Simple but rarely optimal.

Random / TTL-based

Random eviction is surprisingly competitive and dead simple. TTL-based evicts whatever's closest to expiring.

11 — AdvancedTwo-tier caching (L1 + L2)

Why pick between in-process and Redis when you can have both? High-scale systems often layer them like a CPU cache hierarchy.

Each server checks its local L1 first, then shared L2, then DB. Writes invalidate via pub/sub.

The flow:

  1. Read arrives at App server 2. Check L1 (its own in-process map). Hit? Return. Miss? Continue.
  2. Check L2 (Redis). Hit? Populate L1, return. Miss? Continue.
  3. Query database. Populate L2 and L1. Return.
  4. On write: update DB, update L2, publish invalidation message to a pub/sub channel.
  5. All other servers receive the invalidation message and drop that key from their L1.
Why this works so well

Hot keys get absorbed by L1 with zero network cost. Cold-but-shared keys get served by L2 across the fleet. The pub/sub layer keeps L1 caches roughly coherent. You're essentially building a CPU cache hierarchy for your distributed application.

12 — AdvancedCache stampede (thundering herd)

A classic failure mode that brings down systems at the worst possible moment — when a popular cache key expires.

The problem

You have a popular cache key serving 10,000 requests per second. Its TTL expires. At that exact instant, all 10,000 concurrent requests see a cache miss simultaneously. All 10,000 fire identical queries at the database. Your database — which was happily handling ~100 req/s of "cache misses" — now sees 10,000 in one millisecond.

A single expired key triggers a tidal wave of duplicate DB queries.

Three mitigations

  1. Mutex lock (single-flight). When a request misses the cache, it acquires a lock before querying the DB. Other requests for the same key wait for the lock-holder to finish, then read the freshly populated cache. Only one DB query is made.
  2. Probabilistic early expiry. Don't wait for TTL to actually expire. As the key approaches expiration, each read has a small (and increasing) probability of refreshing it proactively. This spreads refreshes across time so there's no synchronized cliff.
  3. Background refresh. A separate worker periodically refreshes hot keys before they expire. The application code never sees a miss on those keys.

13 — AdvancedConsistent hashing

When you scale your cache across many nodes, you need to decide which node owns which key. Consistent hashing is the algorithm that makes this scale gracefully.

The naive approach (and why it breaks)

Simple sharding: node = hash(key) % N, where N is the number of nodes. Works fine — until you add or remove a node. Now hash(key) % 5 gives different answers than hash(key) % 4, and almost every key is suddenly on the wrong node. Your cache hit ratio collapses to ~0%.

The consistent hashing solution

Imagine a giant ring of all possible hash values (0 to 2³². Place each node at a position on the ring based on a hash of its name. Place each key at a position based on a hash of the key. The key belongs to the first node clockwise from its position.

Adding or removing a node only shuffles ~1/N of keys, not all of them.

In practice, each node is placed at many positions on the ring (called "virtual nodes") so the keyspace is distributed evenly. Redis Cluster, DynamoDB, Cassandra, and most modern distributed caches use variants of this approach.

14 — AdvancedThe hot key problem

One cache key receives a wildly disproportionate share of traffic. The node holding it melts while the rest of the cluster sits idle.

Classic examples: a celebrity's profile during a viral moment, a trending product on Black Friday, a flash-sale item, the homepage feed during breaking news. Even with consistent hashing distributing keys evenly across nodes, one request pattern can hammer one node.

Mitigations

  • Key replication. Store the hot key on multiple nodes. Route reads to a random replica to spread load.
  • Local in-process cache. Cache the hot key in each app server's memory. Most reads never touch the network. This is exactly the L1 in two-tier caching above.
  • Request coalescing. Within a single app server, collapse multiple concurrent requests for the same key into one upstream fetch.

15 — ReferenceA decision framework

When you're designing a caching layer, work through these questions in order. They'll lead you to the right architecture.

  1. How stale is acceptable? Seconds? Minutes? Never? This determines TTL and invalidation strategy. Bank balances need strong consistency; social feeds tolerate eventual.
  2. Read-heavy or write-heavy? Read-heavy → cache-aside is your default. Write-heavy with durability requirements → write-through. Write-heavy with tolerance for loss → write-back.
  3. How many app servers? One server → in-process cache is fine. Multiple stateless servers → you need Redis or similar for shared state.
  4. What's your hit ratio target? Higher targets need bigger caches, smarter eviction, and possibly two-tier setups.
  5. Where are your users? Geographically distributed → CDN cache for read-heavy public content.
  6. Any known hot keys? Anticipated viral content, celebrity profiles, popular products → plan replication or local caching ahead of time.
  7. What happens when the cache fails? Cache-aside lets the app fall back to DB. Write-back risks data loss. Design for graceful degradation.
